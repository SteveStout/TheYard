# ADR: The Nightly Function on the Admin tab

Status: accepted, 2026-10-20. The Azure Function that starts the nightly workflow gets the seventh resource card under Cloud infrastructure, `nightly`, named The Nightly Function: whether its slots fired on time, what its runs on GitHub came to, what it costs line by line, and what it is allowed to do. It is one more definition in the one frame (ADR: One frame for every resource), not a recorder, keep or route of its own, and it never reads anything from the file share the lane works on.

## In plain words

A job that runs at four in the morning fails where nobody is looking. The Function wakes every hour, decides whether the hour is one of its six slots in Central time, and asks GitHub to start a run; the run does the work. Until now, finding out whether last night happened meant opening the portal, then GitHub, then the bill. This card puts the three on one page in the same shape as every other resource: two dials, a chart, four questions and a readout.

What that is worth: the dev side and the infrastructure side of a scheduled job looked at in one place, the same way the site's own resources are.

## Context

The Function `func-jobhunt-ss` runs on Flex Consumption in its own resource group, `RG-JOBHUNT-SS`, with the plan `plan-jobhunt-ss` and the storage account `stjobhuntss` (`infra/jobhunt.bicep`). Flex Consumption on Linux does not honour a time zone setting (learn.microsoft.com/azure/azure-functions/functions-bindings-timer, read 2026-10-20), so its timer fires every hour on the hour in UTC and `CentralClock` decides what the hour is: 4:00 AM Central is the reply lane, and midnight, 8 AM, noon, 4 PM and 8 PM are the records run. Each fires `repository_dispatch` at this repository, which runs `.github/workflows/nightly.yml`.

Three sources answer the card's questions. Azure Monitor counts the Function's on-demand executions and execution units on `Microsoft.Web/sites` as `OnDemandFunctionExecutionCount` and `OnDemandFunctionExecutionUnits`, the latter in megabyte-milliseconds, which is what the free grant is counted in; a gigabyte-second is 1,024,000 of them (learn.microsoft.com/azure/azure-functions/functions-consumption-costs, read 2026-10-20). GitHub's public API lists the workflow's runs without a token. The bill names the Function, its plan and its storage account as three lines.

## Decision

**One slot table, compiled twice.** The slots live in `TheYard.Domain/Features/Admin/NightlySlots.cs`: the slot an hour is, the slots due in a window, the next one, and how a slot is judged from five-minute firing counts (on time when a bucket in its first five minutes counted one, late when the first that did is later in the hour, missed otherwise). The Function compiles the same file through a link in its project, and its `CentralClock` asks the table rather than keeping hours of its own, so the card's idea of a slot can never be the Function's minus a daylight-saving change. `NightlySlotsTests` holds the link, the table on both daylight-saving days, and the judging.

```live path=api/TheYard.Domain/Features/Admin/NightlySlots.cs region=nightly-slots
```

**The two dials are the two that run out.** Runs on time over thirty days, a floor: amber under 95 per cent and red under 90, read on the misses the way the edge's cache dial is. And the month's execution units against the Flex Consumption free grant of 100,000 GB-s a month per subscription (with 250,000 executions), amber at 80 per cent and red at 95 (Azure Functions pricing page, read 2026-10-20). The grant is typed with its source on the constant, because no record Azure returns states it.

**A resource group of its own, a directory of its own.** The card finds the Function by type and the configured name in a second `ResourceDirectory` over the Function's group, built beside the first in the module. The names come from configuration (`Nightly` in appsettings.json, `Features/Admin/Cloud/NightlyResources.cs`), and `LiteralScanTests` now refuses the Function's suffix in the code too.

**No role yet, and the card says so.** The site's identity holds no role on `RG-JOBHUNT-SS`. Until it does, Resource Manager and Monitor answer 403, and the card treats that as an answer: the hour writes `role = missing`, the minute reads nothing, and every line that needs Azure reads "not read: no role on RG-JOBHUNT-SS", the group named from configuration. The run log is GitHub's and still reads. The step is Steve's: Monitoring Reader and Reader for the site's identity on the group, which lets the card read the metrics, the record and the Activity Log and nothing on the share.

**The runs are kept a year, one document each.** The hour reads the last thirty days of runs, and upserts each into the `nightlyruns` container under GitHub's own run id, so a run read on thirty hours is one document; it also writes one document per judged slot when Monitor has the counts. The container is partitioned on the day and keeps a year. The card's view is synchronous, so the hour reads the month back into a small in-process cache the view draws from, newest first. `.github/workflows/nightly.yml` gained a `run-name`, so every run's title names its lane and whether it was a dry run; a run from before it reads "not named" rather than a guess.

**What it is allowed to do, in words.** One role on one share (Storage File Data SMB Share Contributor, proven by `functions/jobhunt/role-check.ps1`), and a token that may send `repository_dispatch` to this one repository. The card says so, and says that nothing from the share is read here. How many share snapshots are kept is not read either: that needs a data role on the storage account, and the account key never goes in the site's settings; the readout prints the Function's own limit, fourteen, held to `ShareSnapshot.Keep` by a test that reads the file.

**Three lines of the bill.** `ResourceCard` takes an optional list of bill names and `ResourceCardInputs` an optional dictionary of their month to date, which `CloudReader` fills from the same cost function; every other card passes neither and is unchanged.

## Consequences

- The rail's Cloud infrastructure group ends with The Nightly Function, after Memory against traffic, with its tone dot read before it is opened.
- The card reads GitHub once an hour, one of the sixty unsigned reads GitHub allows an address an hour.
- Two containers on the existing account, inside the free tier: `nightly` for the minutes and hours like every card, and `nightlyruns` for the year of runs. Both are a person's `az` command from their definitions, as every container is.
- The chart shades every Monday and Friday in Central days, the two days the schedule keeps free, through the chart's existing bands.
- Until the role is granted, the dials read "not read" and the card's tone is unread; that is the truth, not a fault.

## Where it sits

Domain gains the slot table, its first rule shared with a project outside the six, which is why it reads no clock and has no I/O. Data gains the two run records. Application gains the run log's port and its memory adapter beside the other memory keeps, Infrastructure.Cosmos its document adapter, and the host the card's view, rows, reader, GitHub reader and cache under `Cloud/`, wired in the cloud slice's module. Single responsibility: the slots are one file both readers compile. What would change it: a second Function, at which point the names become a list and the card a pair.

## Addendum, 2026-10-21 (1.0.4.10): GitHub first, the log a durable copy

1.0.4.9 shipped the card against a run log that was always there in its tests and never there on the live site. Neither container exists yet (`nightly`, `nightlyruns`), and two things followed. The one recorder returned before any card's hour when the card's own keep was missing, so the GitHub read never ran; and even when it ran, the card's cache was filled only by reading the log back, which needs `nightlyruns`. Read live on both names on the morning of 21 October, the card said "no runs read yet" and "nightly off · bookkeeping off" while `nightly.yml` listed ten runs, that morning's 04:00 reply run among them. The sentence above, "the run log is GitHub's and still reads", was not true in code.

From 1.0.4.10:

- **GitHub is the source of the card, the log its durable copy.** The hour fills the cache from GitHub's answer whatever the log says. When `nightlyruns` is there, the runs are also kept in it and the older runs it holds are folded in beside GitHub's, which is what lets the card show a run GitHub no longer lists. When GitHub refuses, the cache is read back from the log if there is one, and the hour says "not read: GitHub answered" and the status.
- **An hourly card is read with no keep.** `CloudRecorder` still reads an hourly card's hour once in its hour when the card's keep is missing, holds it in memory (`LiveHour`), and appends nothing; the minutes are not read at all, since nothing could keep them. `CloudReader` draws such a card from that held hour and asks the recorder once the held hour is older than the card's staleness. The card's note says so: "the nightly container is not there yet; the card reads live until it is."
- **Empty is unread, not off.** The Gates line says "on" or "off" only of a list that was read; with no runs it reads "not read yet" and why.
- **Every "not read" says why**: no hour kept yet, the keep's own reason, no role on the group, or GitHub's answer. `ResourceView.LiveRead` says why no minute is kept on every card.
- **An optional token.** `Nightly:GitHubToken`, when set as a web app setting, is sent as a bearer token, so the read draws on its own allowance rather than the sixty unsigned reads an hour App Service's shared outbound addresses split. None is kept in the repository, and with none set the read is unsigned as before.
- **Words.** The readout is "The nightly job", the slots are "the reply run" and "the records run", and the run table's column is "Run"; "lane" is no word of the site's.

Before the two containers exist the card shows GitHub's runs and gates, the hour's role sentence, and "not read" with its reason on every Azure line; it keeps no history and its chart is empty. Creating them is still a person's `az` command from their definitions. `NightlyCardTests` holds all of it: a run log that is not there beside three listed runs, the gates on an empty list, the reasons, and the recorder with an hourly card and no keep.

## Addendum, 2026-10-21 (1.0.4.22): a GitHub hiccup is the run log's alone, and an empty group is resolved

## Addendum, 2026-10-24 (1.0.4.53): the six processes write a run line each

Every one of the Function's six processes (AtsSweep, DailyCard, Merger, MergerHealth, Nightly, SheetMirror) writes one line a run, at its end, in a finally, so a run that threw still writes it: `process:<Name> outcome=<word> took_ms=<n> started=<UTC>`, a one-word detail when there is one, and its counts (RunLine in JobHunt.Application, RunLines in the host). The outcome is one of six words: success; late, with the seconds after its slot, when it started more than a minute after its scheduled minute; blocked, with the reason (google_settings, google_token, mismatch); failed, with the exception's type; planned, for a shadow run that acted on nothing; unchanged, for a run that found nothing to do or whose switch is off. The inbox pass folds its pass.log line into the same record; its counts are read out of its parts' lines by a pattern a count (read, archived, leads, leads_passed, unjudged, waiting).

What a run line never carries: an address, a message body, a file's contents or a sentence. A detail is one word of letters, digits and underscores, a count's name is lower case, and anything else is dropped before the line is written; RunLineTests holds it with an address in a detail and in a part's line.

How it reaches Application Insights: the line is an information log, which the Functions host sends as a trace in the invocation's own operation, beside the request row the host already writes for every invocation (name, time, duration, success). The Admin tab joins the two by the operation id, so a run from before this version still reads from its request row, success or failed. The plan was a request row named `process:<Name>`; that needs the Application Insights SDK in the worker, a second telemetry pipeline beside the host's, for a row the host already writes. The health route also answers the processes' switches by name (ATS_SWEEP, LEADS, LEADS_LIST, TRIAGE, REPLY_ON_HUMAN, MERGER, APPENDS, NIGHTLY_ANY_HOUR, SHEET_MIRROR, DAILY_CARD), each a plain word or "set", never another setting: the site's identity holds Reader, which cannot list an app's settings, and the card needs the words only.

The six summaries are now the plain-words descriptions the card shows, with the technical notes they held kept as remarks, and Program.cs holds the paragraph that says what the app is (region what-it-is).

## Addendum, 2026-10-24 (1.0.4.54): the six processes on the card

The card gains a description and a section for each of the Function's six processes, from the approved mockup J:\mockups\TheYard-Function-processes-mockup.html. Nothing the card already drew changed: the two dials, the chart, the five questions and the readout are where they were.

The shape is one request per run, and the run line beside it. The Functions host writes a request row for every invocation (name, start, duration, success); since 1.0.4.53 each process also writes its run line in the same operation. The site reads both from the Log Analytics workspace the two Application Insights components send to, with the Log Analytics Reader role the Application Insights card already holds, joined on the operation id: `InsightsProcessRuns` holds the one Kusto shape (the runs of the six, with the outcome from the line, or from the request's success for a row from before the lines) and asks it for a page of one process, its totals, the days folded in Central time, or each process's newest. A history lists every run of the inbox pass, the Sheet mirror and the health route; for the merger, the clock and the daily card it lists the runs that did something and counts the rest, because a pass that merged nothing every minute is a count, not a row.

What a run line carries and never carries is the 1.0.4.53 addendum's rule, and the route keeps it: `GET /api/admin/cloud/nightly/runs/{process}?window=7d&page=1` answers twenty runs a page with when, how long, what each came to in words, what it read and wrote as one sentence built from its counts by one table a process (ProcessWords), and a link that opens the run's operation in the workspace's Logs. It is public like the card, because nothing in it is not already on the card or in the health route, and a name not among the six is a 404 problem.

The route is public and a fresh page is two workspace queries through Resource Manager, whose limits the Application Insights card shares, so the route has a guard (`GuardedProcessRuns`, after a three-seat review of the first cut): a page is kept two minutes by its process, window and page, the page number stops at fifty (a thousand runs back), and past thirty fresh reads in a minute the route says it is busy instead of asking again. The card's own read is kept two minutes too, failure included, so a workspace that is down is asked once in two minutes, not on every poll. A run line's detail is held to one word when it is read, as when it is written.

Why the description is read from the code: the words on the card should be the words in the code at the version deployed, not a second copy that drifts. Each timer file marks its summary with a `summary` region and Program.cs marks its paragraph `what-it-is`; the image carries `functions/jobhunt/*.cs`, and the card reads the regions through the same live-sample reader the documents use (behind a shared port, so the Cloud slice does not reach into the Docs slice). The switches are read from the Function's health route, which reads the app's settings and answers the seven switch names with plain words; the site's Reader role cannot list an app's settings itself, and this way it never sees any other setting.

Two departures from the mockup, both the operator's look winning over the drawing: each process section wears the site's panel (`op-glass`: its ground, its top rule and its corner brackets, with the mockup's tone edge on its left), because every box on a page wears the look and the coverage check reads every page for it; and a narrow card stacks each run, every value under its column's name, instead of scrolling the table sideways, because an Admin table fits or stacks and never scrolls (25 September).

What is not built: the mockup's per-process extras that come from somewhere other than the run lines (the clock's GitHub run number and snapshots kept, the Sheet mirror's blocked row from the plan file, the daily card's header line). ## Addendum, 2026-10-26 (1.0.4.93): five lines that misled a reader

A read of every process's lines on 25 October found five places where a line said something a reader would take the wrong way. None lost data; each made a figure on the card or in a log mean less than it seemed to.

- **The lead import's refused count left out refused companies.** A company the rules turned away was written in the file's notes only, so "0 refused" could sit beside a refused company. It now counts every refusal, a file, a company or a lead. Its count of companies was a count of saves, and a company named in three files counted three times (199 on 25 October for 141 companies); it now reads "companies saved" and counts each company once a pass.
- **The daily card was written every hour.** The check that skips an unchanged card compared the whole body, and the body carries ages ("last line 7 h ago") that change every hour, so the unchanged path never ran (24 of 24 runs wrote the card). Decided: the comparison strips the age words before it compares, and the card itself keeps them, because they are what tells Steve how fresh each line is. - **A Sheet plan the gate stopped read as planned.** The mirror's plan stops at the first row it may not copy (by the gate's design; 142 rows behind one on 25 October), and that pass reported "planned", so the card showed a quiet shadow day. A stopped plan is now `blocked`, detail `gate`, and its sentence says the rows after the stop wait; it names no row's company.
- **The ATS sweep read the same messages every half hour.** The 41 messages it leaves in the inbox were each read whole and their threads listed every pass, about 4,000 Gmail calls a day. It now keeps `ats-sweep/judged.tsv`, one line a message it left: the id, the thread, its senders and the tracker's hash. A message it left before is not read again while its thread's senders and the tracker are unchanged; it is counted with the ones it left. ## Addendum, 2026-10-29 (1.0.4.114): the card is fed by a push, and GitHub is read to reconcile

Until this version the run log was filled one way: once an hour the card's reader asked GitHub's public API for the workflow's last thirty days and kept what it answered. That read is unsigned unless a token is set, GitHub allows sixty unsigned reads an hour per address, and App Service shares its outbound addresses with every other site on it, so the card's own freshness depended on an allowance it does not control. The design note J:\mentor\CLOUD-NIGHTLY-FEED-DESIGN-2026-10-27.md put three ways of feeding a Cloud card to the owner and he chose option A, the push pattern the Claude usage card already uses, and the nightly card as the first one to wear it.

**The push.** `POST /api/admin/cloud/nightly/run` takes one run, behind the operator's key in `X-Admin-Key`, checked before any body is read, exactly as `POST /api/admin/usage` is (ADR: Every Claude lane reports its usage). The route is `NightlyRunRoutes`; the handler is `KeepNightlyRunHandler`, a command because a push is a write from outside (ADR: A request is a query or a command), and it writes through `INightlyRunLog.UpsertAsync`, the same port the hourly read already upserted into. The document's id is GitHub's own run id, so a run posted twice is kept once and a workflow may post again after a failure without the card counting a run twice. Nothing in Azure changed for this: `THEYARD_ADMIN_KEY` already lived in the repository's secrets for the usage report, and the route's key check already existed.

**What the wire carries, and what it does not.** The posted body is GitHub's own facts for the run and nothing made of them: the id, the run number, the event, the display title, when the run was created, how long it had run by the time it posted, and what the job had come to at that step. The slot, who started it, the lane and whether it was a dry run are **not** on the wire: the route reads them off the event and the title with `GitHubRuns.LaneOf`, `NightlySlots.Local` and the same by-function or by-hand rule `GitHubRuns.Parse` uses on GitHub's list. So a run the workflow posted and the same run read from GitHub are one document, field for field, which `NightlyCardTests.A_run_pushed_and_the_same_run_read_from_github_are_one_document` holds by parsing GitHub's own JSON for a run and reading the wire for it and asserting the two are equal. Had the slot been taken from the wire there would be two rules for the Central wall clock and one day they would differ.

**The one fact that can differ, and why GitHub is still read.** The workflow reports `job.status` at the posting step. That is the run as the job knows it there, and GitHub's final conclusion can be something else: a later step can fail, and the run can be cancelled after the post. So the reader keeps reconciling. `NightlyRunReader.ReadAsync` now asks the log first: while the log holds runs and the next slot the schedule has after the newest of them has not come due (`NightlyRunReader.Current`, over `NightlySlots.Next`), and GitHub was read inside the day (`NightlyRunReader.Reconcile`), the hour answers from the log and asks GitHub nothing, and says so in its own words ("N runs kept" rather than "N runs read"). GitHub is read when a slot came due with nothing posted for it, and once a day whatever arrived, and its copy replaces the pushed one, because GitHub is the authority on a run it lists. An empty log is never current: nothing kept says nothing about what ran.

**A night with no push still draws.** A workflow that could not reach the site, a missing key, a site that refused the post: the slot comes due, the newest kept run is older than it, and the hour falls back to the read it has always done. The run log row now carries a line saying which of the two this hour read (`NightlyRows.RunsFrom`), so a reader never has to infer it, and a GitHub read that failed says the log's runs are what is shown and why GitHub did not answer.

**The workflow's step** sits beside the usage report in `.github/workflows/nightly.yml`, region `nightly-run-report`, under `if: always()`, and never fails the run: a missing key leaves the step on 0 with one line in the summary, and a refused post writes one line and goes on. The night's work matters more than its report. The step reads nothing from GitHub's API, so it costs no allowance: every fact it posts is in the run's own contexts, and the start it posts is the first step's clock rather than GitHub's `created_at`, which the daily reconcile then corrects to the second.

**What is not built, by the owner's ruling.** The campaign card's push was the design note's first recommendation but needs an `ADMIN_KEY` app setting on `func-jobhunt-ss` to come from the Function, which is an Azure change and the owner's alone; the counts the campaign card reads come through SQL views the site already reads with its own identity, and the nightly workflow on GitHub has no SQL access, so there was nothing to push from there. The owner chose the nightly card first for that reason.

**One thing this version did not change, found while reading it.** `GitHubRuns.LaneOf` names two lanes, `nightly` and `bookkeeping`, and the workflow has since gained two dispatch types, `triage` and `leads`. A run of either reads "not named" on the card, and it did before this version too. Both paths agree about it (`NightlyCardTests.A_dry_run_by_hand_and_a_dispatch_the_lane_table_does_not_name_read_the_same_either_way` holds that), so the push changed nothing here; naming the two new lanes would change what the card shows and belongs in a version of its own.

The tests: `NightlyCardTests` gains the push's cases (the reader preferring the log, a due slot with nothing pushed falling back, the daily reconcile, the posted run equal to the read run, the rules, the handler with a fake log and no host, the row's line and the workflow's step), and `AdminEndpointsNightlyRunTests` holds the route through the host at each status it declares.
